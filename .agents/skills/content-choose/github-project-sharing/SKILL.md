# GitHub 项目知识分享

## 内容路由

仅在本片选择 github-project-sharing 时使用。主 Agent 首次选择本片内容类型时读取一次统一内容要求及所选形式，之后策划、画面实现和视觉预检沿用同一份要求，不按制作阶段拆分或重复注入。通用的 Skill 与形式选择写入唯一 editorial-plan.json 的 preproduction.contentRoute；本 Skill 专属的观看承诺、故事、例子与结果镜头写入 preproduction.sharing。未选择本 Skill 时不要求、不填写 sharing，后续沿用已选路由。
single-short 为单项目短分享，集中讲清一个任务与结果；single-deep 为单项目深入介绍，围绕同一任务展开关键机制与操作。默认 single-short，深入介绍由用户选择。平台名称不决定内容形式或时长；导演执行模式仍以实测配音120秒为界。

## 内容与叙述

先明确观众看完能理解或完成什么，把这句话作为 viewerPromise。用 story 说明完整故事的因果推进和结尾如何兑现承诺；用 example 描述贯穿的具体输入、关键行动、变化与结果用途。把内容写进完整旁白、purpose、visualDesign 和 continuity。
第一次出现术语时交代它在当前任务中的作用。优先解释项目怎样改变任务，避免串读功能、英文名词和缩写。项目身份帮助观众定位，名称与仓库页面不能代替价值展示。正向用途归纳落到前面呈现的具体例子。
为关键变化和承诺兑现选择实际画面，resultShotIds 指向承载核心结果或收束的已规划镜头；允许同一结果分布在多个镜头，允许结果前置。每镜写清观众观察对象、可理解的变化、结果落点与下一镜关系，选择并准备实际所需的组件源码、必要依赖、用法、演示及图片/SVG/媒体，交付本地链接。
交付前、配音前，在同一研究任务中自检并修正：开场承诺是否被正文与结尾兑现；贯穿例子是否讲清任务、变化和结果；术语是否有任务意义；每项重要讲述是否有对应分镜及已准备材料；是否存在重复铺垫或无关内容。材料查看后如修改故事或镜头，重新完成这项自检。修正直接写回策划案，不另交自检报告或评语。先让观众知道看哪里，再呈现当前变化，给关键结果留出可读的观察时间。复杂界面按表达需要裁切、突出关系或重画重点；运动服务注意力与因果推进。阅读关键文字时可稳定画面，过程可精简，切换应带来新信息或新的观察关系。保留自由 JSX 和自主组合，不套固定布局、对象或动作。
承诺与 resultShotIds 是表达目的，不冻结剪切点。拆分合并时用 planShotIds 延续目的，保证关键变化和结果可追随，开头与收束互相呼应。长片导演统筹全片节奏，镜头子代理在分配范围内遵守同一形式及共享设计。

## 视频流程要求

视频要在开头提出问题，然后使用动效配合仓库截图展现本项目在github上收获的stars数量并说明本项目可能能解决例子中的问题，不要出现明确数字，使用例如6万多的表述。然后中间用贯穿例子说明项目如何解决当前问题，展示关键变化和结果落点。结尾收束承诺兑现，强调结果用途，一句话推荐观众去尝试本项目。每镜明确目的、画面过程、结果落点、旁白线索与前后连续关系；不增加无关报告或候选评语。

## 内容与画面自检

主 Agent 在实际画面上执行视觉预检，不交给独立审查代理。
结合策划承诺、故事、例子、结果位置与当前批次字幕，检查实际连续画面：项目怎样帮助当前任务是否可理解；关键变化与结果是否可见；术语是否已有任务意义；画面是否推进当前讲述；核心结果是否在看清前消失；是否存在重复、突兀跳跃或未兑现收束。按内容复杂度判断阅读时间，不设切换频率、镜头数或运动种类配额。
仅对实际查看区间作结论，全片意图不能代替未查看画面的证据。沿用时间、图片证据与 blocking/major 严重程度及修复路径；minor 不妨碍主要信息，允许通过、不强制修复，不保存具体问题或可选修复建议，也不保留对应的查看证据、范围、观察或通过记录。
纯画面问题由导演修复并复用有效配音；必须改变故事或旁白的问题返回研究策划。最终由人工完整观看和试听批准。
